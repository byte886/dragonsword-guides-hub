# 项目背景与决策日志

> 文档定位：记录项目的历史背景、关键决策和选择理由，让任何接手的AI都能理解"为什么项目是现在这个样子"。
> 核心原则：每个决策都要可追溯——做了什么、为什么、什么时候、效果如何。

## 一、项目起源

### 1.1 项目来源
- 项目名称：AI出海游戏热词站21天实战
- 项目目标：通过搭建游戏攻略热词站，承接Google自然搜索流量，通过广告和联盟变现
- 参与时间：2026年8月
- 参与者：用户（新手起步，逐步进阶为项目主导者）

### 1.2 为什么选这个方向
- 路线选择：在"追热词赚流量钱"和"切长期痛点赚用户付费钱"两条路线中，选择了路线A（热词站）
- 选择理由：轻量化HTML站，快速上线，变现周期短，适合新手
- 变现模式：Google AdSense广告 + 游戏联盟佣金

## 二、关键决策日志

> 按时间倒序排列，最新的决策在最上面。每条决策包含：决策内容、选择理由、备选方案、效果验证。

### 决策1：选定游戏 DragonSword: Awakening
- **时间**：关卡1
- **决策**：选定 DragonSword: Awakening 作为目标游戏
- **选择理由**：
  - 新游戏（2026年7月23日发布），竞争少，有流量红利
  - 韩国开发商Hound13，有一定玩家基础
  - Steam评价"特别好评"（约87%），游戏质量有保障
  - 关键词KD（关键词难度）较低，有排名机会
- **备选方案**：其他同期新游戏
- **效果验证**：关卡1-3顺利完成，关键词和素材资源充足

### 决策2：选择5种语言
- **时间**：关卡4规划阶段
- **决策**：网站支持英文、中文、韩文、俄文、日文5种语言
- **选择理由**：
  - 英文：主力市场，搜索量最大
  - 中文：国内玩家群体大，且中文攻略站竞争相对小
  - 韩文：开发商是韩国公司，韩文玩家基础好
  - 俄文：俄文攻略站常有独家深度内容，且俄文玩家搜索需求大
  - 日文：日本游戏市场大，动作RPG受众广
- **备选方案**：只做英文（工作量小但市场窄）/ 增加更多语言（如泰文、西班牙文，但翻译成本高）
- **效果验证**：137个页面完成，多语言结构正常

### 决策3：纯静态HTML技术栈
- **时间**：关卡4
- **决策**：使用纯HTML+CSS+JS，不使用框架和后端
- **选择理由**：
  - 部署简单（GitHub Pages免费托管）
  - 加载快，SEO友好
  - 维护成本低，不需要服务器
  - 适合内容型站点
- **备选方案**：Next.js / WordPress / Hexo等
- **效果验证**：网站审核95/100分，性能良好

### 决策4：域名 ds-guides.wiki 已购买
- **时间**：关卡1规划，关卡5购买
- **决策**：域名为 ds-guides.wiki，通过 Spaceship 注册
- **选择理由**：
  - .wiki后缀适合攻略/百科类站点
  - ds是DragonSword的缩写，简短好记
  - guides明确站点定位
- **备选方案**：dragonsword-guides.com（更长但更完整）
- **状态**：已购买（2026-08-15），DNS 托管在 Cloudflare

### 决策5：部署平台选择 Vercel（而非 GitHub Pages）
- **时间**：关卡5
- **决策**：网站部署在 Vercel（Hobby 免费计划），而非原计划的 GitHub Pages
- **选择理由**：
  - Vercel 对静态站有全球 CDN、自动 HTTPS、自动部署
  - 与 GitHub 集成好，push 自动部署
  - 教程关卡5要求用 Vercel + Cloudflare
  - GitHub Pages 也可行，但 Vercel 的域名绑定和重定向更方便
- **备选方案**：GitHub Pages（免费但配置较繁琐）、Netlify、Cloudflare Pages
- **效果验证**：部署成功，dragonsword-guides.vercel.app 可访问

### 决策6：Cloudflare 代理状态选择 DNS only（灰色云）
- **时间**：关卡5
- **决策**：Cloudflare DNS 记录的代理状态设为 DNS only（灰色云），不开启 Proxied（橙色云）
- **选择理由**：
  - Vercel 已自带全球 CDN 和自动 SSL，Cloudflare 代理会造成双重 CDN
  - 橙色云 + Vercel 容易出现重定向循环、SSL 模式冲突
  - 纯静态站暂时不需要 Cloudflare 的 DDoS 防护
  - 以后需要时可随时开启
- **备选方案**：橙色云（需配置 SSL 模式为 Full Strict，有兼容性风险）
- **DNS 配置**：
  - A 记录：@ → 216.198.79.1（Vercel 官方推荐 IP）
  - CNAME：www → df9ecd0750052516.vercel-dns-017.com（Vercel 推荐值，2026-08-15 从 cname.vercel-dns.com 更新）

### 决策7：GA 跟踪代码外部化为单一 JS 文件
- **时间**：关卡5
- **决策**：将 115 个 HTML 中内嵌的 GA 代码提取到 js/analytics.js，所有页面引用同一文件
- **选择理由**：
  - Measurement ID 只维护一处，换 ID 不用改 115 个文件
  - 不破坏 SEO，不引入框架，纯静态
  - 用 defer 属性加载，不阻塞页面渲染
- **效果验证**：commit 5b2c100 已推送，所有页面统一引用

### 决策8：GitHub 用户名改为 byte886，双仓库结构
- **时间**：关卡4-5
- **决策**：
  - GitHub 用户名从 softwarecheng 改为 byte886
  - 仓库1：byte886/dragonsword-guides（纯网站代码，04-website/）
  - 仓库2：byte886/dragonsword-guides-hub（完整项目，04-website 作为 git submodule）
- **选择理由**：
  - 代码仓库保持轻量，Vercel 只部署代码
  - hub 仓库保存教程、文档、素材等完整项目资料

### 决策9：信息源采用五维来源矩阵
- **时间**：关卡3
- **决策**：素材搜集从英文权威站、中文站、小语种站、Wiki、社区/视频五个维度获取
- **选择理由**：
  - 避免单一来源的偏差
  - 小语种站（特别是俄文、韩文）常有英文站没有的独家内容
  - 交叉核验提高内容准确性
- **效果验证**：23个页面素材充足，50+信息源

### 决策10：关键词清洗采用四步法
- **时间**：关卡2
- **决策**：关键词挖掘后经过过滤→去重→合并同义词→筛选四步清洗
- **选择理由**：
  - 原始关键词数量大、质量参差不齐
  - 需要去除品牌词、作弊词、社区引流词
  - 合并同义词避免页面重复
- **效果验证**：从大量原始词清洗出23个核心关键词

### 决策11：GSC 采用域名验证方式，通过 Cloudflare Domain Connect 一键授权
- **时间**：关卡5
- **决策**：GSC 添加资源时选择"网域"（Domain）类型而非"网址前缀"（URL prefix），通过 Cloudflare 一键授权验证
- **选择理由**：
  - Domain 类型覆盖所有子域名（www、m、blog）和 http/https
  - Cloudflare 支持 Domain Connect 协议，一键授权自动添加 TXT 记录，无需手动复制
  - 以后加子域名不用重新验证
- **效果验证**：验证即时通过，sitemap 提交后状态为"成功"，发现 115 个页面

### 决策12：apex 域名（ds-guides.wiki）作为主域名，www 308 重定向到 apex
- **时间**：关卡5
- **决策**：Vercel 中 ds-guides.wiki 设为 Production，www.ds-guides.wiki 设为 308 重定向到 ds-guides.wiki
- **选择理由**：
  - 域名更短更好记，适合分享
  - canonical URL 已统一为 https://ds-guides.wiki/，不用改 115 个文件
  - Cloudflare A 记录已配好，apex 直接服务无技术问题
- **备选方案**：www 做主域名（需改 115 个 HTML 的 canonical，URL 多 4 个字符）
- **效果验证**：curl 确认 apex 返回 200，www 返回 308 到 apex

### 决策13：修复英文子页面 canonical 缺少 /en/ 前缀的问题
- **时间**：关卡5
- **决策**：22 个 en/*.html 的 canonical 从 https://ds-guides.wiki/filename.html 修正为 https://ds-guides.wiki/en/filename.html
- **原因**：原 canonical 指向不存在的根目录路径（返回 404），会导致搜索引擎困惑
- **效果验证**：commit 5182b59 已推送，线上 canonical 正确

## 四、踩过的坑（避免重踩）

### 坑1：SimilarWeb的KD列默认不可见
- **现象**：在SimilarWeb关键词研究中找不到KD（关键词难度）列
- **原因**：KD列在表格右侧，需要用左右箭头滚动才能看到
- **解决**：在关键词表格中点击右箭头，切换到KD列
- **避免**：操作手册01中已明确标注此步骤

### 坑2：目录位置放错
- **现象**：项目移交文档最初放在了网站代码目录内，后确认应与代码目录平级
- **解决**：移到平级目录，并重命名为05-operation-guides
- **避免**：文档目录与代码目录平级，不嵌套

### 坑3：文档写成了结论报告
- **现象**：第一版移交文档直接列出了关键词清单、KD数值等结论，新窗口AI无法复现过程
- **原因**：混淆了"成果报告"和"操作手册"
- **解决**：全部重写为操作手册型，每步写清楚工具、输入、操作、输出、判断标准
- **避免**：文档定位先明确——是给人看结论还是教AI怎么做

### 坑4：浏览器自动化点击坐标偏差
- **现象**：用脚本自动点击页面元素时，坐标有偏差导致功能测试不准
- **原因**：不同屏幕尺寸、缩放比例影响坐标
- **解决**：改为用户手动验证关键交互功能
- **避免**：涉及UI交互的测试优先人工验证，不依赖坐标脚本

### 坑5：角色技能名称来自社区整理
- **现象**：部分角色技能名称是从社区攻略整理的，可能与官方有差异
- **解决**：标注"来自社区整理，建议游戏内验证"
- **避免**：重要数据优先从官方/Wiki获取，社区数据需交叉核验

### 坑6：Playwright sandbox 池耗尽
- **现象**：Playwright 命令报 SandboxPoolExhaustedError，所有 Bash 命令无法执行
- **原因**：之前的 Playwright 进程未正确 detach，残留进程占满 sandbox 池
- **解决**：`pkill -9 -f playwright; pkill -9 -f "@playwright"` 清理残留进程，或重启豆包
- **避免**：每次 Playwright 操作完必须 detach；异常时 kill-all

### 坑7：Cloudflare 扫描导入注册商默认停放记录
- **现象**：Cloudflare 添加站点时自动导入了 2 条 A 记录（54.149.79.189、34.216.117.25），不是用户配置的
- **原因**：Spaceship 对新域名默认配置停放记录（指向广告页），Cloudflare 扫描时全部导入
- **解决**：删除多余停放记录，只保留 Vercel 的 A 记录和 CNAME
- **避免**：Cloudflare 扫描后必须逐条审核 DNS 记录，不要直接确认

### 坑8：GA 账户命名混乱
- **现象**：GA 中有 3 个账户（deweb.me、softwarecheng、www.s187.com），命名不规范
- **原因**：之前测试时随意创建，用网站名命名账户不符合 GA 层级结构
- **解决**：清空所有旧账户，按"组织/个人 → 媒体资源（域名）→ 数据流"重建
- **避免**：GA Account 用个人/公司名命名，Property 用域名命名

### 坑9：英文子页面 canonical 缺少 /en/ 前缀
- **现象**：22 个 en/*.html 的 canonical 指向 https://ds-guides.wiki/filename.html，该 URL 返回 404
- **原因**：生成页面时英文子页面的 canonical 路径未包含 /en/ 目录
- **解决**：批量 sed 替换，将 canonical 改为 https://ds-guides.wiki/en/filename.html
- **避免**：新增页面后用 curl 检查 canonical 是否返回 200；canonical 必须与实际 URL 一致

## 五、项目约束与红线

### 5.1 内容红线（绝对不能碰）
- 作弊相关内容（mod、trainer、cheat、crack、key等）——广告联盟禁止
- 成人内容
- 盗版/破解相关
- 社区引流词（reddit、discord等，用户搜完直接走，留不住）

### 5.2 质量红线
- 所有事实性内容必须有真实来源，严禁AI编造
- 重要信息必须2个以上独立来源交叉核验
- 每个信息点都要记录来源链接

### 5.3 工作方式约束
- 严格按步骤操作，禁止跳步
- 关键节点主动确认，不擅自猜测意图
- 敏感操作（登录、密码、支付）由用户手动完成
