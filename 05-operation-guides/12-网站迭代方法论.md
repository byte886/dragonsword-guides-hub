# 网站迭代方法论：七轮迭代法

> 文档定位：**方法论手册**。游戏攻略站上线后的系统化迭代方法，每轮只解决一类问题，用数据验证效果。
> 来源：4群林广恩（MistriaFans，Fields of Mistria 攻略站）实战经验 + 项目实践总结。
> 核心数据：GSC 三个月 1089 点击、5.94 万展示、1.8% CTR、8.8 平均排名；移动端 PageSpeed 74→97。
> 整理日期：2026-08-26。

---

## 一、核心原则

### 1.1 每轮只解决一类问题

不要把内容、首页、埋点、语言和广告塞进同一次发布。

**为什么：**
- 数据变好时，得知道大概是哪一类调整起了作用
- 数据变差时，得知道该把哪一批改动撤回去
- 即使这一轮没有增长，结论也该留得下来，下一轮不必从头试

**判断标准：** 只要准备发布的改动里同时出现以下两类以上，就先拆开：
- 内容或新页面
- 首页结构
- 埋点和统计口径
- 语言或翻译
- 广告或脚本

拆不开，就还没到发布的时候。

### 1.2 迭代卡（每轮开始前必须写）

写不出来，说明这一轮还没想清楚，先不要改。

迭代卡只写五句：
1. **这一轮只解决什么问题**
2. **我准备做哪一类修改**
3. **什么结果算有效**
4. **什么时候停止继续改**
5. **如果改坏了，怎么恢复**

**开发规范：**
- 每轮改动单独 commit，不顺手塞进其他功能
- 上线后不马上再改一轮，先等 Google 重新抓取，或等一个完整的数据周期
- 改完看迭代卡上预先写死的那一两项有没有动，不要事后用"这个版本改了很多东西"给自己打分

## 二、七轮迭代详解

### 第一轮：质量基线（结构、语言、来源）

**目标：** 先把网站变成一个可以放心迭代的版本。结构和语言不过关，后面看到收录差、点击低，也说不清是哪步出的问题。

**怎么找到问题：**

1. **程序检查**：和 AI 列出清单，写小程序逐个扫描页面。清单只问四件硬事：
   - 这一页有没有明确的主要正文
   - 是不是只有一个主标题（H1）
   - 来源齐不齐
   - 不同语言是不是在讲同一主题

2. **语言审查**：句子自然不自然、有没有串语言，程序不好判。把各语言页面交给 AI 检查：
   - 句子是不是目标语言
   - 有没有混进别的语言
   - 读起来是否像人写的

3. **人工确认**：打开被标记的页面，亲自点来源、图片和站内链接。程序或模型标红的，只有确认过才动手改。

**怎么判断：** 这类问题跟流量多少无关。结构错误、语言串页、缺少来源，对就是对、错就是错，应该先修。点击率、停留时间、要不要扩写，都需要更多数据，不能和这一轮混在一起判断。

**怎么优化：**
1. 修正页面正文结构，让人看得见的正文和代码标出来的正文一致
2. 清掉串语言残留，并复查其他语言有没有同类问题
3. 给版本、平台、兼容性这类容易吵、也容易过期的说法补上来源
4. 核对各语言是否指向同一组主题，有没有孤立页或错配页
5. 把上述规则收成全站静态检查和上线验收，避免下一轮更新再把同样的错带回来

**改完看什么：** 不看排名有没有涨。重新生成网站，再跑一遍静态检查，并用浏览器抽查各语言。结构、语言、来源、链接都过了，这个站才有可以比较的基线。

---

### 第二轮：网址信号（canonical、www、.html）

**目标：** 解决 Google 抓取和网址不一致的问题。同一份内容如果活在好几个地址上，Google 很难判断该收哪一个。

**典型问题：**
- 用户访问不带 `.html` 的地址直接掉进 404（如 `/farm-layout` 实际存在的是 `/farm-layout.html`）
- 带 www 和不带 www 的地址混用过
- canonical URL、sitemap、页内链接指向不一致

**怎么找到问题：**

1. GSC → 左侧「网页」→ 找到 404、重定向、重复网页对应的问题项 → 看 Google 列出的示例网址
2. 复制示例网址 → 左侧「网址检查」→ 先看 Google 有没有收录、选了哪个规范网址 → 再用浏览器打开原地址，记下会不会跳、跳几次、最终页能不能打开

**怎么判断：** 如果同一份内容同时出现 www、非 www、带 .html、不带 .html 多个地址，问题在网址信号，不在正文。只要规范网址、站点地图和用户实际打开的地址对不上，就先修这一层。

**怎么优化：**
1. 全站统一用一个主域名（如 `https://www.example.com` 或 `https://example.com`）
2. 让规范网址（canonical）、多语言标注（hreflang）、站点地图（sitemap）和页内链接都指向这套地址
3. 给不带 .html 的旧地址做永久跳转（301/308），跳到现在的正确页面
4. 未知地址保持真实 404，不要把所有错误网址都扔回首页
5. 部署后逐页核对状态码、跳转次数和最终落点

**改完看什么：** 先确认旧地址只跳一次，而且是永久跳转，落到正确页面。再到 GSC 发起验证，看 Google 选中的规范网址是不是和网站声明的一致。Google 还没重新抓这批页之前，不要继续改同一批页面。

---

### 第三轮：玩家任务（一页只讲一件事）

**目标：** 不再按关键词批量建页，改为解决玩家任务。最早做内容时，很容易看见一个词就想做一页，后来会生出很多只有两三句的薄页面，也可能让几页去抢同一批搜索。

**怎么找到问题（GSC 数据分析详细步骤）：**

1. 打开 GSC → 左侧「效果」→ 日期切到「28 天」
2. 滚到折线图下方的数据表 → 打开「查询」→ 按展示次数从高到低看
3. 先圈出展示高、点击低的候选词，但先不把它们叫成「持续需求」
4. 点进一个搜索词 → 上方折线图会只留下这个词 → 再用顶部日期，对比当前 28 天和前 28 天，确认两个周期都有展示
5. 切到旁边的「网页」→ 看 Google 拿站内哪一页接这个词
6. 把这个词丢回 Google → 看前排给的是短答案、表格、图片、清单还是工具
7. 再搜 `site:example.com 搜索词` → 检查站里是不是已经有一页在回答同一件事

**筛选示例：** 把「展示超过 300、点击不超过 3」的行圈出来，再按玩家要做的事合并不同写法：
- 两个房屋升级词合计 1,090 次展示、2 次点击，CTR 约 0.18%
- 两个角色词合计 902 次展示、3 次点击，约 0.33%
- 作为对照，某个攻略页有 431 次展示、10 次点击，约 2.32%

这样先排出候选任务，再逐个看趋势、平均排名和对应网页。

**怎么判断：** 圈出候选之后，只问三个问题：
1. 这个搜索是不是一件独立的事？
2. 现有页面能不能自然接住？
3. 新页面能不能给出比一段话更具体的答案？

任务不独立的长尾，合并进已有页面。不为了把页面做多再拆一页。

**怎么优化：** 新增页面时，先写两行再动笔：
- 玩家打开这一页，是要完成哪一件事
- 这一页有什么是别页给不了的

写不出来，就不建新页。

**改完看什么：** 更精确的搜索有没有进到对应那一页；人进来以后还会不会点相关内容。页面是不是又多了几页。

### 第四轮：首页入口（从游戏介绍改成任务入口）

**目标：** 首页跳出率明显高于全站时，把首屏从游戏介绍改成更清楚的下一步入口。

**怎么找到问题（GA4 探索详细步骤）：**

1. GA4 → 左侧「探索」→ 点「自由形式」→ 日期先用最近 28 天
2. 左侧「变量」里加维度「着陆页 + 查询字符串」→ 再加指标「会话数」和「跳出率」
3. 中间「设置」→ 把「着陆页 + 查询字符串」放到「行」→ 把「会话数」和「跳出率」放到「值」
4. 点结果表里的「跳出率」列 → 从高到低排
5. 「过滤器」里把「会话数」设成「≥ 10」→ 先拿掉只有一两次访问却显示 100% 跳出的页

**判断示例：** 最近 28 天全部流量里，首页 `/` 有 256 次会话，跳出率 87.5%。同期全站 58.8%。这才把它列为优先检查对象。

如果还想看是不是自然搜索的问题，再加一个过滤器：「带来会话的默认渠道组」完全匹配 Organic Search。如果自然搜索下首页只有 6 次会话，样本太小，不能写成「自然搜索进来的人看了首页就走」。

**怎么判断：** GA4 只能回答先查哪一页，不能回答该改成什么样。跳出率把首页圈出来，然后根据网站定位和页面检查，决定测什么方案。

比如攻略站，站里已经有新手、送礼、赚钱、鱼类、矿洞、恋爱和版本这些具体内容；如果首屏却主要在介绍游戏，没把下一步说清楚，对一个只想先知道下一步去哪的人来说，先看游戏介绍就绕远了。

**怎么优化：**
1. 把常用攻略入口放到更靠前的位置
2. 用明确按钮，把人送去新手、送礼、婚恋这些具体任务
3. 游戏介绍还留着，但放到任务入口后面
4. 官方预告片改成点了才加载，避免首屏先去拉一段用户未必会看的视频

**改完看什么（提前写死判断标准）：**
1. `guide_card_click`：有多少人点了首页攻略卡（新入口有没有被看见、被用到）
2. `internal_link_click`：有多少人从首页继续走进站内其他页（首页有没有把人送到下一步）
3. 首页跳出率和第二页访问：直接离开的人少了没有，继续往下看的人多了没有

**判断逻辑：**
- 攻略卡点击、站内点击、第二页访问一起增加，同时首页跳出率下降 → 「把任务入口提前」得到支持
- 按钮点击增加，但第二页访问没增加 → 入口引人注意，后面的页没接住
- 这几项都没改善 → 停止继续改同一套方案，改去查流量质量、加载速度或统计口径

### 第五轮：打开速度（PageSpeed 优化）

**目标：** 页面打开慢，人可能还没看见内容就走了；内容不对路，人是看见了也不想继续。两项同样重要，但要分开改。

**怎么找到问题：**

1. 打开 pagespeed.web.dev → 贴上首页地址 → 点「分析」
2. 先看手机端 → 记下性能分数和核心网页指标 → 再往下看诊断项
3. 需要定位具体文件时 → Chrome 打开同一页 → `Command + Option + I` 打开开发者工具 → Network → 刷新页面
4. 按 Img、Media、JS 筛选 → 用 Size、Time 排序 → 找出体积大或加载慢的资源
5. 再用 Lighthouse 分析一次 → 确认问题能稳定复现，不是单次波动

**怎么判断：** 移动端最初是 74 分。诊断指向图片、首屏加载和缓存这些实现问题，所以这一轮只处理性能，不改首页文案，也不动任务入口。这样改完以后，分数变化才说得清原因。

**怎么优化：**
1. 压缩图片，并按实际展示尺寸输出，避免手机去加载用不上的大图
2. 收紧首屏资源和缓存策略
3. 预告片先出本地海报，用户点播放后才加载 YouTube
4. 单独测过「把分析脚本推迟加载」有没有收益。对照之后没有改善，就退回官方标准写法。代码已经写了，也不勉强留着

**关键原则：** 跟 AI 确认每个调整会影响什么才做决定。

**改完看什么：** 移动端从 74 分到 97 分，只说明性能优化生效了。它不能证明首页内容已经帮用户把下一步找着。快不快，看 PageSpeed；内容对不对路，看行为数据。

---

### 第六轮：测量校准（排除自己的测试流量）

**目标：** 日常报告里是不是还混着自己的测试。尺子不准，就不改页面。

**怎么找到问题：**
- GA4 管理 → 数据设置 → 数据过滤器 → 检查内部流量过滤器是否配置并生效
- 确认开发/测试环境的流量是否被排除
- 确认机器人过滤是否开启（GA4 默认已启用 IAB/ABCe 机器人过滤）

**怎么判断：** 如果数据里混着自己的测试访问，所有行为数据都会失真。先把尺子校准，再看页面数据。

**怎么优化：**
1. 配置内部 IP 规则，排除开发/办公网络的流量
2. 确认数据过滤器状态为"生效"（不是"测试"）
3. 检查 GA4 增强衡量设置是否正确（网页浏览、滚动、出站点击、站内搜索、文件下载、视频互动）

**改完看什么：** 确认排除后的数据与之前的数据差异在合理范围内，没有因为排除测试流量导致数据异常波动。

---

### 第七轮：一次只改一类（写成规矩）

这是前面六轮做下来后总结的规矩，已经在"核心原则"部分详细说明。

**关键执行点：**
- 每轮开始前写迭代卡（五句话）
- 每轮改动单独 commit
- 上线后等一个完整数据周期再评估
- 改完只看迭代卡上预先写死的指标
- 动了就留下记录，没动就按停止条件收手

## 三、对本项目的应用建议

### 当前状态评估

我们的项目（ds-guides.wiki）目前处于：
- ✅ 第一轮（质量基线）：页面结构、多语言、来源基本过关
- ✅ 第二轮（网址信号）：canonical、308 重定向、sitemap 已配置
- ⚠️ 第三轮（玩家任务）：内容规划还可以更精细，部分页面可能偏薄
- ⚠️ 第四轮（首页入口）：首页跳出率偏高，需要优化首屏入口
- ❌ 第五轮（PageSpeed）：尚未系统优化
- ⚠️ 第六轮（测量校准）：GA 增强衡量已配置，内部流量过滤需确认
- ✅ 第七轮（一次只改一类）：已在 AGENTS.md 中体现

### 建议的下一轮迭代

**迭代卡示例：**
1. **这一轮只解决什么问题**：首页跳出率偏高，用户进入后不知道下一步去哪
2. **我准备做哪一类修改**：首页结构——把热门攻略入口提前到首屏
3. **什么结果算有效**：首页跳出率下降、内页点击增加、第二页访问增加
4. **什么时候停止继续改**：如果 2 周后这三项都没改善，停止改首页，转查流量质量或加载速度
5. **如果改坏了，怎么恢复**：git revert 到上一个 commit
